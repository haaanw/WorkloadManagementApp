## Anti-Pattern Verdict

This does not read like generic generated SaaS UI. The core idea is specific: an austere sports-science instrument with square cards, low decoration, and nocebo-safe recommendations. The problem is governance, not taste: the live app has enough competing implementation choices that the finished product no longer cleanly embodies its own design document.

## Priority Issues

### P1 - Dark mode is specified but currently disabled at multiple layers

`DESIGN.md` defines a dark-primary, light-supported adaptive system, but the app forces light mode in the SwiftUI scene, Info.plist, and UIKit controllers.

Evidence:
- `/Users/hanwen/Desktop/Tonus/WorkloadApp/App/WorkloadApp.swift:102-106` applies `.preferredColorScheme(.light)`.
- `/Users/hanwen/Desktop/Tonus/workload management/workload-management-Info.plist:46-47` sets `UIUserInterfaceStyle` to `Light`.
- `/Users/hanwen/Desktop/Tonus/WorkloadApp/App/AppShellUIKitPrimitives.swift:9-13` forces `.light` on controllers/windows.
- `/Users/hanwen/Desktop/Tonus/WorkloadApp/App/AppShellUIKitPrimitives.swift:362-390` reapplies that style in the live scroll controller path.

Impact: The adaptive color-token system cannot be trusted, users cannot exercise iOS appearance preferences, and dark-mode contrast claims in the design system are unverified.

Recommended fix: remove the app-wide light locks, replace `applyTonusLightInterfaceStyle()` with an appearance-respecting helper if needed, and add screenshot coverage for light and dark Today/Train/Profile.

### P1 - ColorTokens no longer match the current Tuwa v2 design system

`DESIGN.md` says the app should use the 2026-06-17 Tuwa v2 palette and specifically lists the Swift literals to edit. `ColorTokens.swift` still carries a restored v1 material palette and a cooled-travertine accent comment.

Evidence:
- Design source: `/Users/hanwen/Desktop/Tonus/DESIGN.md:52-123` and `/Users/hanwen/Desktop/Tonus/DESIGN.md:158-168`.
- Implementation drift: `/Users/hanwen/Desktop/Tonus/WorkloadApp/Utilities/ColorTokens.swift:41-75`.
- Example mismatch: design accent is `#7FB3CC` dark / `#2E6B86` light, while code uses `0xA8AEA9` / `0x62706B`.

Impact: The fresh Today screenshot shows the hero number as a subdued grey-green instead of the live/actionable stone-blue. The product loses the one intentional color signal the design system depends on.

Recommended fix: update `ColorTokens.swift` to exactly match the DESIGN.md table, including `accentSubtle`, zone colors, and chart aliases. Treat this as a design-system migration, not a cosmetic tweak.

### P2 - Live UIKit shell breaks the strict 0pt/no-shadow design contract through system chrome

The audited Today screen is mostly square and disciplined, but the floating tab bar is rounded/glass-like and visually outside the International Style grammar. The implementation relies on UIKit `UITabBarAppearance`/`UINavigationBarAppearance`, while the app-level design requires square, hairline-only surfaces.

Evidence:
- Live shell entry: `/Users/hanwen/Desktop/Tonus/WorkloadApp/App/AppShell.swift:24-31`.
- UIKit tab setup: `/Users/hanwen/Desktop/Tonus/WorkloadApp/App/AppShell.swift:561-577`.
- UIKit navigation appearance: `/Users/hanwen/Desktop/Tonus/WorkloadApp/App/AppShell.swift:117-160`.
- Fresh screenshot attachment from `/tmp/TonusUIAudit_Today.xcresult` shows the rounded floating tab bar despite square cards.

Impact: The top-level navigation is the most repeated UI element; if it speaks a different visual language, the whole app reads less intentional.

Recommended fix: either implement a custom square tab rail consistent with DESIGN.md, or explicitly amend DESIGN.md to allow native rounded iOS chrome. Right now the code and spec disagree.
