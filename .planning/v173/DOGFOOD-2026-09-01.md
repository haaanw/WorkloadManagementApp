# HAN dogfood report — official 1.7.2 build (2026-09-01)

Findings from HAN's device use, with CLAUDE's source diagnosis. This file is
the input brief for the voice/logging round-2 lane (v1.7.3 features 1+2) and
adds one launch-performance item.

## Bugs

### B1. PDF program import fails — Edge Function 400

Screenshot: Import Workout → PDF → "Failed to parse workout: Edge Function
returned a non-2xx status code: 400."

**Root cause (verified in source):** `parse-workout/index.ts` rejects
`workout_text.length > 10_000` with a 400. The app extracts PDF text
on-device (PDFKit text layer, OCR fallback) and sends the WHOLE extraction;
a real multi-week program PDF easily exceeds 10,000 chars. No app-side
truncation exists (`WorkoutLLMImportService` has none), so every
substantial program PDF 400s. Secondary defect: the sheet surfaces the raw
transport error instead of the edge function's message.

**Fix direction:** raise the plan-mode cap (log mode can keep 10k) AND
pre-process app-side — strip page furniture, collapse whitespace, and chunk
or truncate intelligently with a "which weeks?" prompt if still oversized.
Surface the server's error message, mapped to human copy.

### B2. Voice capture dies after ~10 s

**Design intent (verified):** `SpeechCaptureService` runs unlimited capture
with 50 s segment rotation; recognition errors ROTATE the segment (never
kill); `LogCaptureSheet` has no silence auto-stop. `VoiceDictationCard`
(live per-set) auto-stops after 1.5 s of silence BY DESIGN.

So a ~10 s forced quit is either:
(a) HAN was in the live card — 1.5 s silence stop is far too aggressive for
    how people actually speak between thoughts; or
(b) a narrative-capture bug the design does not intend — candidate
    mechanisms: audio-session interruption not recovered, or a rotation
    loop failure on device.
**Fix direction:** reproduce on device first. Regardless of (a)/(b): the
live card's silence window becomes generous + user-visible (e.g. ≥5 s with
a countdown affordance), and narrative capture gets an on-device soak test
(3+ min continuous with pauses).

### B3. Launch friction — "Preparing Tuwa" ~10 s on every open

**Root cause (verified, `AppRouter.swift:136-203`):** the loading screen
blocks on a serial network chain before first paint: `hasSession` (Keychain
+ possible token refresh) → if the sync clock says stale (true every
morning): `await syncService.pullAll(...)` — a FULL pull of every entity —
→ `subscriptionService.logIn` (RevenueCat round-trip). Only then does the
UI route. On mobile networks that is the observed ~10 s.

**Fix direction — optimistic local-first launch:** if a local Athlete
exists and the Keychain has a session, route to `.main` IMMEDIATELY and run
pullAll + RevenueCat logIn + pipelines in the background; `@Query` updates
the UI when data lands. Blocking is legitimate ONLY on fresh install /
missing athlete (bootstrap + zombie paths, which stay). RevenueCat has
cached CustomerInfo — logIn never needs to block. Target: cold open to
dashboard < 1 s, sync banner if a background pull is still running.
Overnight HealthKit data: the recovery pipeline already runs on dashboard
appear; a later enhancement is HK background delivery + BGAppRefresh so
the morning number is computed before first open.

## UX findings

### U1. Import is buried and fragmented

Import lives behind the "+" menu as four flat entries (PLAN TODAY / IMPORT
WORKOUT (AI) / MY PROGRAMS / IMPORT PROGRAM (TEXT)) — two different
importers with unclear names, no PDF mention, no prominence. For a product
whose core is "bring YOUR plan," program import must be a prime, visible
door — especially for a fresh account (the No Templates empty state should
sell import, not template creation).

### U2. HAN's product ruling — plan-led logging is the spine (2026-09-01)

The primary logging model becomes: import your program once (text, PDF,
photo, voice) → Tuwa proposes each day's workout from the program position
→ fatigue level + morning check-in ("How are you feeling today?") adjust
the day's volumes/loads → the athlete follows guided numbers → logging
during the session is VOICE-LED against that day's plan; typing exists to
correct errors, not to author. The whole loop must feel smooth — logging is
the product's strongest function. Guardrail framing: steady progress
without exhaustion or injury risk (claim rails still bind: no injury-
prevention claims in copy).

This is the CORE-REDEFINITION thesis finally made concrete in the daily
loop: user-authored plan in, readiness-modulated numbers out, zero-friction
capture closing the loop. Pieces that EXIST today: plan-mode parse
(text/PDF/photo), WorkoutTemplate/MY PROGRAMS, Plan Today + TodayVerdict
resolvedPlan path (verdict → prefilled workout), morning probe, voice
logging. What round 2 builds is the CONNECTION: program → calendar
position → today's proposal → check-in-adjusted numbers → voice-first
guided logging.

## HAN dispositions (2026-09-01)

- **B1 (PDF): both fixes approved** — raise the plan-mode cap with app-side
  preprocessing ("which weeks?" when oversized) + human error surfacing.
- **B2 (voice cutoff): HAN was in the NARRATIVE sheet → treat as a bug;
  reproduce on device.** Ruling: narrative capture gets NO silence
  auto-stop at all — the silence window is effectively invisible; capture
  ends only by user action. (The live card keeps auto-stop but generous.)
- **NEW R1 — transcript quality mandate:** the recognition path must filter
  filler words and stutters automatically, keep only information-bearing
  content, and hand the app/LLM organized, formatted text. Design space:
  local cleanup pass over the transcript + the LLM prompt's normalization
  duties; measure accuracy before/after on real narrations.
- **B3 (launch): approved** — optimistic local-first launch, cold open
  < 1 s. Plus the standing goal: data READY at any open — background sync +
  overnight processing (HealthKit background delivery + BGAppRefresh so the
  morning number is computed before first open). Ship the optimistic launch
  first; background freshness is its follow-on, not its blocker.
- **U2 (plan-led logging): approved.** Demo-first with MULTIPLE exploration
  directions, iterated over several rounds, then a finalized version.
- **Sequencing (HAN): the widget checklist completes FIRST; the launch-fix
  and round-2 lanes open after that.**
