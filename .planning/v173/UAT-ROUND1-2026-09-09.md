### U4 · why recent watch workouts were missed — DIAGNOSED, four defects

Ruled out first: **authorization is not the cause.** `HKWorkoutType.workoutType()`
has been in `readTypes` since `a96941a` (2026-04-21), long before HAN's grant, and
the three walks proved reads were working.

Four defects, all in the retired `WorkoutImportService`, ranked by how well each
explains "three stale walks with the recent session missing":

1. **The list was fetched once per app process and never again.** `.task` on the
   Log tab (`WorkoutLogView.swift:434`) is the only trigger. In a `TabView` the
   child is built on first selection and kept, so the task never fires a second
   time — no foreground refresh, no observer, no anchor. A watch workout reaches
   the phone's HealthKit store MINUTES after it ends, routinely after that one
   fetch has already run, and nothing asked again. **This is the primary cause**
   and it is the only one that also explains why the list looked frozen.
2. **A three-day window with no catch-up.** The service defaulted to 7 days; the
   call site passed 3 (`WorkoutImportBanner.swift:203`). Anything older was
   invisible permanently.
3. **Everything under five minutes was discarded** (`:233`) — a short sprint block
   or skill session never appeared at all.
4. **The dedupe was a POINT match** — suppress if any session started within five
   minutes (`:226-230`). It failed in both directions: a watch started ten minutes
   into a logged session read as a second session (double-counted load), and two
   genuinely different sessions four minutes apart lost one silently.

**Not determinable from source:** which of 1/3/4 hit HAN's specific missing
workout. Stated rather than guessed. All four are closed by the rebuild regardless.

### U4 · what was built

`WatchWorkoutMatcher` (pure) + `WatchWorkoutImportService` replace the banner, which
is DELETED. Anchored `HKAnchoredObjectQueryDescriptor` — HealthKit tracks what the app
has seen, so each workout is handed over exactly once however often the import runs;
a 14-day window bounds only the FIRST run so a new install never back-logs years of
walks. Runs on every foreground (`AppRouter`) and on the Log tab's appearance.

The dedupe guard is interval OVERLAP (≥50% of the shorter span), plus
`WorkoutSession.healthKitWorkoutUUID` as an idempotency key so a lost anchor or a
reinstall cannot double-log. It fails SAFE: a session logged twice inflates ATL, ACWR
and the fatigue index for four weeks invisibly; a session missed once is visible in
history and addable by hand.

Effort → RPE: `HKQuantityType(.workoutEffortScore)` (the athlete's own rating) with
`.estimatedWorkoutEffortScore` as fallback, both read via
`predicateForWorkoutEffortSamplesRelated(workout:activity:)`, iOS 18+. Both are 1–10
category-ratio scales asking the same question, so the map is the identity with
clamping — no invented curve on the one subjective input the load model rests on. The
fallback matters: a session with no RPE contributes ZERO internal load and zero
training stress while still counting toward session density. Raw samples stay on
device; the derived `sessionRPE` is what syncs.

A `healthKitReadTypesGeneration` counter re-asks a legacy grant once for the new
types, raised at the first moment the app actually holds a new watch workout — so the
permission sheet arrives attached to the thing it is for, not at a cold foreground.

The surface is a quiet `From watch` mark in the history row's marginalia. No banner,
no Add row, no RPE sheet.

**Scoped out, and it is a real limit: this is foreground-automatic, not background.**
True background delivery needs
`com.apple.developer.healthkit.background-delivery`, which the app does not hold
(`workload management.entitlements`) and which is a provisioning change, not a code
change. The session is already there when the athlete opens the app; it does not
appear while the phone is in a pocket. **HAN decides whether to add the entitlement.**

### Background delivery for watch workouts (U4 follow-on; HAN's entitlement landed 2026-09-13)

The entitlements file now carries `com.apple.developer.healthkit.background-delivery`
(HAN's Xcode step, re-done today and verified in the file before any code was written).
Wiring: `HealthKitService.enableWorkoutBackgroundDelivery()` (`.immediate`) +
`observeWorkouts` (an `HKObserverQuery` on the workout type), driven by
`WatchWorkoutBackgroundDelivery` in `WatchWorkoutImportService.swift` — registered in

called on EVERY path — import logged, import declined, observer error — through one funnel
(`handleDelivery`), because three unacknowledged deliveries switch background delivery off
until relaunch. Eight tests pin it, including the failure path: `enableDelivery` throwing
(no entitlement, or the simulator) is recorded and nothing else changes; a registered
observer that never fires leaves the foreground path as the only trigger, and a source
fence asserts `AppRouter` still calls `WatchWorkoutImportService.run` directly.

**No second dedupe layer.** The observer runs the same `run`; the anchored query hands
each workout over once and the service's `isRunning` guard folds a simultaneous
foreground run and observer run into one.

### Round 2 — root causes (read-only diagnosis, verified in source, 2026-09-13)

**U15 / U14 / U17 are one chain.** `ProgramScheduleService.activate` takes no start
date (`ProgramImportSheet.swift:1146` → default `.now`, `:114`), and
`materializedEntries` anchors program week 1 to the ISO Monday of the import week
(`:77`, `weekAnchor` `:34-39`) then silently drops every day before today (`:91`
`if dayDate < todayStart { continue }`). A Sunday import therefore creates ZERO
week-1 entries; the header still prints `W1 OF 8`; the first real session is
W2D1 next Monday. `movePosition` (`:142`) repeats the same anchoring. Today's
`TodayProposalSection` (`:40-61`) shows the bring-card whenever `vm.display == nil`,
which only means "no planned entry dated today" — it never consults
`fetchActiveProgram`, so the card shows on every rest day and every un-entried day
(the Log tab checks the program and hides correctly, `WorkoutLogView.swift:162`).
After 7d3f704 the ONLY live door to `ActiveWorkoutSheet(resolvedPlan:)` is the
verdict card on Today (`TodayProposalSection.swift:54`, needs a designation and a
non-pending decision); `DashboardView.swift:311-317` and
`WorkoutLogView.swift:266-273` are dead branches that only ever assign nil.

**U12 has three parts.** (1) `NotificationService.swift:66-74` builds the body with
`localizedUserNotificationString(forKey:arguments:)` against a catalog value using
`%1$lld…%4$lld` (`Localizable.xcstrings:8247/8253`); the API archives the
arguments as objects and substitutes `%@` only, so each positional prefix is
consumed and the residual `$lld` ships verbatim — character for character what
the screenshot shows. (2) The schedulers pass zeros (`ProfileView.swift:590-598`,
`DashboardView.swift:202-210`) into a `repeats: true` trigger, so the numbers are
frozen forever. (3) There is NO tap handling anywhere (no delegate, no userInfo,
no route): a tap is a plain launch to Today; the weekly review is
`WeeklySummaryCard` low in the Today scroll, double-gated on real data and
`sessionCount > 0`, with no scroll anchor.

**U13 is output volume, not a different path.** All three doors converge on one
`parseProgramText` call, `mode:"program"`, to OpenAI `gpt-4o-mini`
(`index.ts:400`) with no `max_tokens`, no `temperature` (=1.0), no streaming, one
call, no retry. The prompt REQUIRES every week to be emitted in full even when
identical (`index.ts:274`); a 4-day/6-exercise/4-set week is ~3,600 output tokens
≈ 30 s at the model's throughput, so 30–40 s ≈ one expanded block, and >4 weeks
truncates at the 16k ceiling into a 502 after >100 s. PDF and photo are bounded
by what fits on a page; a typed sentence commands an unbounded expansion — hence
PDF < photo < text. The text door also hides its whole wait behind one opaque
spinner (`ProgramImportSheet.swift:889-903`) while the file doors show "READING n
OF m" before the CTA. No timing instrumentation exists in the function.

Fix lanes opened from these (see the pair board): app-side (anchor → next Monday
with a start choice, Today three-way branch, Log-tab door, notification format /
freshness / tap route, honest text-door wait) and edge-function (distinct weeks +
`repeat_of_week`, `max_completion_tokens`, `temperature 0.2`, timing logs; DEPLOY
HAN-GATED). U16 (Trends meaning layer) is being surveyed for a copy proposal.
