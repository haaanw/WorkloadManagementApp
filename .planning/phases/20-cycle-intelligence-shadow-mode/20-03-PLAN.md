<objective>
Wire the shadow loop into the live recovery flow: write Stage-1 predictions (baseline vs cycle-aware) per day, resolve them the next day against observed outcomes, and provide an aggregation that computes baseline-vs-cycle-aware prediction error per outcome. Also record (but never apply) the Plan 02 would-be modifier effects so the shadow data captures "what we'd have done." No user-facing behavior changes — the dashboard recommendation is identical because activation is off.

Purpose: This completes ROADMAP criterion 1 ("shadow-mode analytics silently measure: does cycle phase improve prediction of next-day readiness, wellness, completion, or pain?"). It reuses the Phase 18 machinery already present in `RecoveryPipeline.run` — the injected `CycleTrackingService`, the derived `CycleContext`, and the RecoverySnapshot × MenstrualCycleSnapshot date-join — so the new I/O is minimal. The aggregation is the artifact a future "modifier activation" phase will read to decide whether to flip `CycleModifierActivation.isEnabled`. Everything stays local-only and unsynced (D-13).

Output: `CyclePredictionLogRepository` (mirroring `CycleSnapshotRepository`), `ShadowAnalyticsService` (record + idempotent resolve + MAE aggregation), Stage-1/Stage-2 hooks in `RecoveryPipeline.run`, `DashboardViewModel` passing `CycleContext` into the Plan 02 engine overloads (returning unchanged values, activation off), and tests for record/resolve idempotency + MAE math.
</objective>
