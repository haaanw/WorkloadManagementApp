W1 (MAIN — monotony saturation): The Wave-2 fix z-standardises endurance + strength per-stream then adds a +3.0 offset and sums (LoadDistributionEngine lines ~196-201). The summed series has mean ≈ 6 and SD ≈ 1-1.4 → Foster monotony (mean/SD) ≈ 4-6 → StrainRiskEngine does `clamp01(monotony / 3.0)` (Constants.monotonyNormaliser = 3.0, StrainRiskEngine L96/L136) which SATURATES to 1.0 for EVERY gate-passing log. The monotony channel is pinned at max regardless of the actual training distribution; strength only "moves" monotony inside the already-clamped region, so the surfaced factor is a constant. FIX (PREFERRED, also fixes W2): drop the z-standardise+offset hack and build ONE real-unit combined daily series by converting each day's strength hard-set strain to an sRPE-EQUIVALENT load via a documented multiplier (so a typical hard set maps to a comparable sRPE-load magnitude), summing it with the day's endurance sRPE load, then run classic Foster monotony (mean/SD) on that single real-unit series. Foster monotony then lands in the natural ~1-3 range so clamp01(/3.0) is meaningful and strength contributes proportionally.

W2 (gate/series divergence): Today completenessGate() runs on the raw `dailyLoadSeries` while monotony runs on the SEPARATE standardised `monotonyInputSeries` — a structured log can pass the gate (.computed, confidence gateFactor 1.0) yet have monotony=nil on the other series, and StrainRiskEngine then uses `monotony ?? 0` at FULL weight (reads as zero-monotony-at-high-confidence). The single-series approach makes the gate and monotony share one series so .computed ⇒ monotony non-nil automatically. ALSO harden StrainRiskEngine defensively so any residual .computed-with-nil-monotony degrades to the reduced-weight fallback, never 0-at-full-weight.

W3 (windowing off-by-one): Apply the same half-open fix StrengthLoadEngine.windowedRange already uses (L373-385, `diff >= lower && diff < upper`) to LoadDistributionEngine lines ~84, ~167, ~291 so a "window of N days" spans exactly N calendar days. Re-derive any window-count oracle tests.

TEST GAP: existing StrainRisk tests hand-feed monotony 1.5/2.0/3.0; nothing exercises the REAL LoadDistributionEngine.distribution() → StrainRiskEngine.fuse() path, which is exactly how W1 hid. Add a real integration test feeding a VARIED multi-day log end-to-end and asserting the monotony factor is NOT saturated at 1.0 and DOES vary with distribution.

Purpose: monotony stops being a pinned constant and becomes a meaningful, distribution-sensitive shadow signal; the gate and the metric agree; windows are exact; and a real integration test guards against the regression.
Output: rewritten monotony-input path in LoadDistributionEngine (single real-unit series), half-open windows, defensive StrainRiskEngine fallback, re-derived LoadDistribution oracle values, new end-to-end StrainRisk integration test.
